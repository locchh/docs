# Amazon Simple Storage Service

**Where it sits on the exams.** **Amazon Simple Storage Service (Amazon S3)**, the Regional object storage service, stores data as objects in buckets and exposes it through application programming interfaces (APIs) rather than as disks or a shared Portable Operating System Interface (POSIX) file system. It is a core choice in SAA-C03 tasks 1.3, 2.1, 2.2, 3.1, and 4.1, and in SAP-C02 tasks 2.4, 2.5, 2.6, 4.3, and 4.4. The exam rule of thumb is to choose S3 for elastically scaling object data, then choose access, protection, replication, and lifecycle settings from the workload's latency, durability, residency, and cost requirements.

## Object storage and the S3 data model

S3 is object storage. An object contains a value, which is the byte sequence being stored, a key that identifies it within a bucket, system and optional user-defined metadata, access-control information, and, when versioning is enabled, a version ID. Objects can range from zero bytes to 50 TB. A single `PUT` can upload up to 5 GB, so larger objects require multipart upload. The documented binary maximum is 48.8 TiB because a multipart upload can contain at most 10,000 parts and each part can be at most 5 GiB. The console is a client of the same service, not a different storage path.

An object key is the whole name, such as `orders/2026/09/11/part-0001.parquet`. General purpose buckets have a flat object namespace. The slashes in that key let tools group and display prefixes as folders, but a prefix is not a directory with its own inode, capacity, locking, or rename operation. The console can create a zero-byte object whose key ends in `/` to make an empty folder appear. Moving a conventional S3 "folder" means copying all objects under one prefix and deleting the originals. Applications should therefore treat keys as identifiers and objects as complete values, not depend on in-place byte updates or filesystem locks. The one exception is narrow: directory buckets in an Availability Zone support appending data to an existing object. General purpose buckets do not, so a question about appending to objects in ordinary S3 is asking you to replace the object or to choose a file system instead.

System metadata includes properties such as content length, content type, storage class, encryption state, and last-modified time. User-defined metadata is supplied with `x-amz-meta-` headers at upload and is returned with the object. Changing user-defined metadata normally requires copying or rewriting the object because metadata belongs to an object version. Object tags are separate key-value labels. Tags are especially useful in authorization, replication filters, lifecycle rules, cost allocation, and operations that must change independently of the object's bytes. Metadata describes the object; tags drive management. At very large scale, use **S3 Inventory**, the scheduled flat-file catalog of objects and selected metadata, or newer S3 metadata capabilities instead of repeatedly listing and inspecting every object.

An entity tag (ETag) identifies a particular object representation and supports conditional requests such as `If-Match` and `If-None-Match`. It is often, but not always, an MD5 digest for a single-part object uploaded without an encryption mode that changes the calculation. Multipart uploads produce composite ETags, and encrypted objects do not always have an MD5 ETag. Do not use an ETag as a universal integrity checksum. S3 supports explicit checksums, including cyclic redundancy check and Secure Hash Algorithm families, and current clients calculate and send checksums for uploads. Conditional writes and deletes use the current representation's ETag to prevent a concurrent writer from silently replacing or deleting a value that changed after it was read.

The storage-type distinction is a frequent exam setup. **Amazon Elastic Block Store (Amazon EBS)**, persistent block storage for compute instances, presents a volume that an operating system formats and mounts, so it fits databases, boot volumes, and applications that need block-level random writes. **Amazon Elastic File System (Amazon EFS)**, the managed elastic Network File System (NFS), and **Amazon FSx**, the family of managed file systems for specific protocols and engines, present shared files, directories, permissions, and filesystem semantics. S3 instead provides an object API, effectively unbounded bucket capacity, rich lifecycle and replication controls, and independent object access. It is the default for data lakes, backups, media, logs, static assets, and durable application blobs, but it is not a drop-in filesystem for software that requires POSIX locking or in-place modification.

**Mountpoint for Amazon S3**, the open-source high-throughput Linux client, translates a limited set of file operations into S3 object calls. It helps analytics and machine learning programs read large S3 datasets through a familiar mount path, but it does not turn general purpose buckets into POSIX storage. Choose EFS or an FSx file system when shared-file semantics are a requirement. Choose EBS when one compute host needs a low-latency block device. Choose S3 when the application can read and replace whole objects and values elastic scale, durability, HTTP access, lifecycle tiering, or cross-Region replication.

The bucket remains the policy, Region, namespace, and management boundary. Storage class is normally selected per object, so one general purpose bucket can hold a frequently read current dataset, infrequently accessed backups, and archived noncurrent versions in different classes. This is why an exam question asking for "the correct data lifecycle" is rarely asking for a separate bucket for each age. It is asking for object classification, a storage-class choice, and lifecycle transitions or expiration that match the access pattern.

## Buckets, keys, consistency, and bucket types

A general purpose bucket is created in one AWS Region, and its objects remain in that Region unless a user or configured feature copies them elsewhere. The bucket name and Region cannot be changed after creation. In the shared global namespace, a name must be unique across all accounts and Regions within an AWS partition. It is 3 through 63 characters and uses lowercase letters, numbers, periods, and hyphens under additional Domain Name System (DNS)-style restrictions. Do not put confidential information in a bucket name because it appears in endpoints. If a globally named bucket is no longer needed, keeping the empty, access-blocked bucket prevents another account from later acquiring the name and receiving requests intended for the former owner. S3 also supports an account Regional namespace whose names are reserved to the account, but shared-global names remain common in exam scenarios.

A request addresses a bucket in one of two URL styles. Virtual-hosted style puts the bucket in the hostname, `https://bucket-name.s3.region-code.amazonaws.com/key-name`, and is the form AWS recommends. Path style puts it in the path, `https://s3.region-code.amazonaws.com/bucket-name/key-name`. Both work in all Regions today. AWS announced a path-style deprecation and then delayed it in September 2020, so path style still functions, but new designs should use virtual-hosted style. This is the practical reason to avoid periods in a bucket name: the TLS wildcard certificate covers only names without dots, so `my.data.bucket` breaks HTTPS in virtual-hosted style. Path-style URLs are also a poor fit for browser-facing website content because they interfere with the same-origin model, where an S3 website endpoint or an Amazon CloudFront distribution is the right answer.

Most bucket-level behavior is a separate API call against the bucket rather than a property set at creation, which is why the exam so often frames a requirement as "which setting would you enable".

```bash
aws s3api put-bucket-versioning --bucket my-bucket \
  --versioning-configuration Status=Enabled

aws s3api put-bucket-encryption --bucket my-bucket \
  --server-side-encryption-configuration '{"Rules":[{
    "ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"aws:kms",
      "KMSMasterKeyID":"arn:aws:kms:us-east-1:111122223333:key/EXAMPLE"},
    "BucketKeyEnabled":true}]}'

aws s3api put-bucket-accelerate-configuration --bucket my-bucket \
  --accelerate-configuration Status=Enabled
```

By default, an account can create 10,000 general purpose buckets, and the quota is adjustable. There is no maximum bucket capacity and no fixed limit on the number of objects in a bucket. Those properties are what the exam means by storage that can scale to future needs. Do not shard data across buckets merely to gain capacity or request throughput. Split buckets when policy ownership, account boundaries, Region, retention, logging, data classification, or administrative delegation genuinely differs.

S3 supplies strong read-after-write consistency in every Region for successful object `PUT` and `DELETE` operations, including overwrites. A subsequent `GET` or `LIST` sees the completed write. Updates to one key are atomic, so a concurrent reader sees either the old value or the new value, never a partial mixture. Strong consistency does not make a multi-object workflow transactional. If an application must atomically update ten objects as one business operation, it still needs an external transaction or manifest pattern. Nor does consistency remove the need for concurrency control when multiple writers race on one key. Conditional requests, versioning, and application coordination solve that problem. A conditional write with `If-None-Match` succeeds only when no object exists at that key, which is the direct way to prevent two writers from overwriting each other on first create. `If-Match` with an ETag gives the complementary compare-and-swap on an expected current version.

General purpose buckets serve the broad S3 feature set and the familiar flat key namespace. **S3 Express One Zone**, the single-Availability Zone high-performance S3 storage class, uses directory buckets in an Availability Zone and delivers consistent single-digit millisecond request latency. A directory bucket organizes keys hierarchically and uses Regional control-plane endpoints plus Zonal data-plane endpoints, but it is still object storage. It does not inherit all general purpose bucket features or POSIX semantics. The application should colocate compute in the selected zone, use current **AWS software development kits (SDKs)**, the language libraries for AWS APIs, and session-based authorization, and accept that a zone disruption can make the data unavailable or cause data loss.

Directory buckets use a different name form that contains the zone ID and `--x-s3`, are unique within the selected zone, and have a default adjustable quota of 100 per account. Object versioning and multi-factor authentication (MFA) delete are not supported for S3 Express One Zone directory buckets. The class supports server-side encryption with S3-managed keys or one customer managed key from **AWS Key Management Service (AWS KMS)**, the managed cryptographic key service, per directory bucket, but not dual-layer server-side encryption or customer-provided keys. These differences make Express One Zone a deliberate performance choice for latency-sensitive temporary or reproducible data, not a cheaper universal replacement for S3 Standard.

S3 also has specialized table buckets for Apache Iceberg tables and vector buckets for vector indexes. Their APIs and data models are purpose-built rather than alternative storage classes for ordinary general purpose bucket objects. If a question asks only for a durable object repository, backup target, data lake landing zone, or static assets, choose a general purpose bucket. If it explicitly asks for low-latency repeated object access by compute in one zone and accepts a zone-level failure domain, consider Express One Zone and a directory bucket.

## Storage classes and retrieval behavior

Storage-class questions are access-pattern questions. Start with four facts: how soon the first byte must be available, how often an object is read, how long it will remain, and whether a single-zone failure may lose the only copy. Then account for object count, retrieval volume, and request volume. A lower per-GB-month storage rate can lose to minimum-size charges, early-deletion charges, transition requests, restore requests, and retrieval fees.

The table is the decision baseline. Availability is the class's design target, not durability and not a service-level agreement. Except for the two one-zone choices, the listed classes are designed to tolerate the physical loss of an Availability Zone.

| Storage class | Best fit and access | Designed availability | Zones | Minimum duration | Minimum billable object size | Retrieval behavior |
|---|---|---:|---:|---:|---:|---|
| **S3 Standard** | Frequently accessed data, millisecond access | 99.99% | At least 3 | None | None | Direct `GET`, no retrieval fee |
| **S3 Intelligent-Tiering** | Unknown or changing access, automatic tiering | 99.9% | At least 3 | None | None | No retrieval fee; archive tiers require restore |
| **S3 Standard-Infrequent Access (Standard-IA)** | Long-lived data read about monthly, millisecond access | 99.9% | At least 3 | 30 days | 128 KB | Direct `GET`, per-GB retrieval fee |
| **S3 One Zone-Infrequent Access (One Zone-IA)** | Re-creatable infrequently read data | 99.5% | 1 | 30 days | 128 KB | Direct `GET`, per-GB retrieval fee |
| S3 Express One Zone | Latency-sensitive, frequently accessed data colocated with compute | 99.95% | 1 | None | None | Direct `GET`, single-digit millisecond access |
| **S3 Glacier Instant Retrieval** | Archive read about quarterly that must be immediate | 99.9% | At least 3 | 90 days | 128 KB | Direct `GET`, millisecond access and retrieval fee |
| **S3 Glacier Flexible Retrieval** | Archive read about yearly | 99.99% after restore | At least 3 | 90 days | 40 KB metadata overhead | Restore first, minutes to hours |
| **S3 Glacier Deep Archive** | Long-term archive read less than yearly | 99.99% after restore | At least 3 | 180 days | 40 KB metadata overhead | Restore first, hours |

All of these classes are designed for 99.999999999 percent durability except Reduced Redundancy Storage (RRS), which is designed for 99.99 percent durability. Durability describes the annual likelihood of retaining objects. Availability describes whether an object can be accessed when requested. S3 Standard and Standard-IA can have the same durability target while different availability targets and price shapes. Replication to another Region solves a distinct risk and policy problem; it is not required merely to obtain multi-Availability Zone durability from a multi-zone class.

S3 Standard is the default and the clean answer for frequently accessed objects, uncertain hot workloads with many small objects, and workloads where retrieval charges would erase storage savings. Standard-IA lowers storage cost for long-lived, infrequently read objects while preserving millisecond access and multi-zone resilience. It bills objects smaller than 128 KB as 128 KB, charges for at least 30 days, and adds retrieval fees. One Zone-IA has the same minimums but stores in one zone. Use it for a secondary copy or reproducible output, never as the only copy of irreplaceable data when the requirement includes resilience to an Availability Zone disaster.

S3 Intelligent-Tiering, the storage class that moves individual objects among access tiers according to observed access, fits data whose pattern is unknown or changes over time. It has a per-object monitoring and automation charge. Objects smaller than 128 KB stay in Frequent Access and do not incur that monitoring charge. Eligible objects move from Frequent Access to Infrequent Access after 30 consecutive days without access and to Archive Instant Access after 90 days, while all three tiers retain millisecond access. A read from the lower low-latency tiers moves the object back to Frequent Access automatically, with no retrieval fee.

The optional Archive Access and Deep Archive Access tiers extend Intelligent-Tiering to asynchronous archives. Archive Access can begin after at least 90 days without access, and Deep Archive Access after at least 180 days; the thresholds are configurable. Reading one of these archived objects requires a restore into Frequent Access. Choose Intelligent-Tiering when uncertainty is genuine and object size makes the monitoring charge reasonable. Do not choose it solely because it sounds automatic if a stable, known access pattern makes a fixed class cheaper.

The **S3 Glacier storage classes**, the S3 bucket-based archival tiers, keep objects and keys in S3 and use S3 APIs. Glacier Instant Retrieval is not offline. It is the archive class for rare access that still needs a millisecond `GET`, with a 90-day minimum and retrieval fee. Glacier Flexible Retrieval and Deep Archive are offline classes. A `GET` does not read them until a restore request creates a temporary readable copy; during that window, the archive and restored copy are both billed. Flexible Retrieval offers Expedited restores typically in 1 to 5 minutes for qualifying urgent retrievals, Standard typically in 3 to 5 hours, and Bulk typically in 5 to 12 hours. Deep Archive offers Standard within 12 hours and Bulk within 48 hours, with no Expedited tier.

For very large restores, typical per-object time is not a promise that an entire petabyte dataset completes at the same time. **S3 Batch Operations**, the managed service for applying one operation to large object lists, can issue restore requests at scale. Flexible Retrieval Bulk retrievals are free, while retrieval request and data charges vary by class and method. The exam usually gives enough constraints to avoid price memorization: "must be available immediately" rules out Flexible Retrieval and Deep Archive; "within 12 hours" can fit Deep Archive Standard; "within 48 hours" and lowest archive storage cost points to Deep Archive Bulk; an unpredictable pattern points to Intelligent-Tiering.

Flexible Retrieval and Deep Archive add 40 KB of per-object metadata overhead: 8 KB billed at the Standard rate and 32 KB at the archive class rate. This and per-object transition requests make millions of tiny objects poor archive candidates. Aggregate small records into larger, independently recoverable objects when the access and compliance model permits. Glacier Instant Retrieval instead applies a 128 KB minimum billable object size.

RRS remains an available legacy storage class, but AWS explicitly recommends not using it because S3 Standard is more cost-effective. It is not accurate to call RRS formally deprecated or removed. The exam answer for noncritical reproducible single-zone data is normally One Zone-IA, and the answer for frequently accessed data is Standard. The original standalone **Amazon Glacier**, the vault-based archival service with its own 2012 API, is distinct from S3 Glacier storage classes and is no longer accepting new customers. Existing vault customers retain access, while new archive designs should use the S3 Glacier storage classes.

## Lifecycle policies and data retention

**S3 Lifecycle**, the rule engine for transitioning and expiring objects, turns a written retention policy into per-object actions. A rule can cover a whole bucket or filter by prefix, object tags, object size, or combinations. Transition actions move current or noncurrent versions to another class. Expiration actions remove current versions or permanently delete noncurrent versions. Other actions delete expired object delete markers and abort incomplete multipart uploads. Lifecycle operates asynchronously, so design against the eligibility date rather than expecting an action at an exact second.

For a nonversioned bucket, expiration permanently deletes the object. In a versioning-enabled bucket, expiration of a current version normally adds a delete marker and makes the former current version noncurrent. It does not reclaim the bytes of older versions. A complete cost and retention design therefore treats current versions, noncurrent versions, delete markers, and incomplete multipart parts separately. For example, keep current reports in Standard, transition them to Standard-IA after a verified cooling period, transition noncurrent versions to a Glacier class, permanently expire noncurrent versions after the recovery window, remove expired delete markers, and abort multipart uploads that were never completed.

New or edited lifecycle configurations prevent objects smaller than 128 KB from transitioning to any storage class by default. This behavior changed in September 2024. A size filter can deliberately allow smaller objects, and a request header can retain the older exception for Glacier Flexible Retrieval and Deep Archive, but the default protects customers from paying a transition request whose cost can exceed the storage saved. An older untouched configuration can preserve the pre-change behavior until it is modified. On the exam, a workload with billions of tiny objects should prompt a per-object cost analysis, not a reflexive transition to the cheapest per-GB tier.

Minimum-duration charges apply even when lifecycle moves or deletes an object early. Standard-IA and One Zone-IA charge for at least 30 days, Glacier Instant Retrieval and Flexible Retrieval for at least 90 days, and Deep Archive for at least 180 days. A lifecycle chain cannot transition within a single rule from one class to another before the first class's minimum period ends. Separate rules can technically cause an earlier move in some cases, but the remaining minimum-duration charge still applies. Build timelines from object creation and from when a version becomes noncurrent, and include both storage periods in the cost model.

Lifecycle is not a substitute for access control, backup validation, or legal retention. A rule can accidentally expire the only copy if its scope is wrong. Versioning provides recovery only until noncurrent versions are permanently deleted. Retention controls can prevent deletion of protected versions even when a lifecycle expiration is due, while lifecycle can still transition the protected version to a colder storage class. Replication rules and lifecycle rules are evaluated independently; if replicas need the same retention behavior, configure lifecycle on destination buckets as well.

S3 Intelligent-Tiering and Lifecycle answer different questions. Intelligent-Tiering reacts to changing access inside one storage class, while Lifecycle applies deterministic age, tag, prefix, and size rules and can expire data. Use Intelligent-Tiering when access cannot be predicted. Use Lifecycle when the business says, for example, "archive audit records after 90 days and delete them after seven years." They can work together, but a deterministic rule that moves every object to an archive tier should not pay an additional monitoring charge without a reason.

**S3 Storage Class Analysis**, the access-pattern analyzer for filtered Standard objects, observes data for 30 days or longer and recommends candidates for Standard-IA. It does not transition objects itself and only recommends Standard to Standard-IA moves. Use its results to improve a lifecycle rule. For broad organization-level visibility and recommendations, use Storage Lens, covered later. The cost-optimized sequence is classify, measure, choose a tier, automate the lifecycle, and then verify that retention and restore tests meet the business requirement.

## Upload, download, and request performance

S3 automatically scales to high request rates. A partitioned prefix can support at least 3,500 `PUT`, `COPY`, `POST`, or `DELETE` requests per second and at least 5,500 `GET` or `HEAD` requests per second. There is no limit on the number of prefixes, so parallel access across ten prefixes can scale reads to at least 55,000 requests per second. These figures are baselines per prefix, not a bucket-wide ceiling. Modern S3 does not require random hash characters at the start of every key. Meaningful prefixes can scale, and additional prefixes provide independent request capacity.

Scaling to a new, much higher request pattern can be gradual. Clients should retry temporary `503 Slow Down` responses with exponential backoff and jitter while S3 adapts. Partitioning a hot workload across several prefixes, issuing requests concurrently, reusing connections, and locating compute in the same Region all increase usable throughput. If objects are encrypted with a KMS key, KMS cryptographic request quotas can become the limiting dependency even when S3 itself can accept more requests. A Bucket Key reduces KMS calls and cost, but quota planning remains part of a high-request design.

Batching has two different meanings in S3 exam questions. For ingest, combine many small logical records into appropriately sized objects when the consumer can process them together. This lowers per-request cost and avoids minimum billable size and archive metadata overhead on every tiny record. Do not combine unrelated records so aggressively that every read must download and rewrite a huge object. For API efficiency, clients can send parallel requests and use high-level transfer managers; S3's object APIs do not provide one ordinary `PutObject` call that uploads an arbitrary list of independent objects as a transaction. For bulk changes to objects already in S3, use Batch Operations, covered later.

Multipart upload divides one large object into independently uploaded parts. AWS recommends considering it at 100 MB because parallel transfers improve throughput and a failed part can be retried without restarting the whole object. A multipart upload can use up to 10,000 parts, each 5 MiB through 5 GiB except that the last part has no minimum. A complete request atomically assembles the object. Until it completes, the parts consume billable storage but no object is visible under the final key. Always complete successful uploads or abort abandoned ones, preferably with a lifecycle action that cleans up incomplete multipart uploads after an operationally safe interval.

The ETag returned for each part is included in the completion request. A full-object checksum is a better integrity control than assuming the completed multipart ETag is an MD5 digest. Upload parts can arrive independently and out of order when part numbers are unique. A transfer manager in a current SDK or the AWS Command Line Interface (AWS CLI) handles concurrency, checksums, retries, and assembly, which is usually less operational work than custom part orchestration.

Large downloads use the same parallel principle. A `Range` header retrieves only a byte interval, and several connections can fetch different ranges concurrently. This raises throughput and limits a retry to the failed range. Objects larger than 5 TB require concurrent `GetObject` requests because one `GET` is limited to 5 TB. Range requests are also useful when an application needs only a header, index, or segment from a large format. They do not understand rows or columns. S3 Select formerly filtered supported structured content within one object, but it is no longer available to new customers; new analytics designs normally use a query service or format-aware application reads.

**S3 Transfer Acceleration**, the bucket feature that routes long-distance client transfers through nearby CloudFront edge locations and the AWS global network, targets uploads or downloads between geographically distant clients and one bucket Region. It uses a distinct virtual-hosted endpoint such as `bucket-name.s3-accelerate.amazonaws.com`. The bucket name must be DNS-compliant and cannot contain periods. Acceleration adds a data-transfer charge and does not make every network path faster, so use the AWS speed comparison tool and enable it when measured long-haul improvement justifies the cost.

Transfer Acceleration is not the same as **Amazon CloudFront**, the content delivery network that caches or proxies content near viewers. CloudFront is the usual answer for repeated global downloads, HTTPS static sites, signed viewer access, and reducing requests to an S3 origin. Transfer Acceleration moves an individual upload or download quickly between a remote client and the bucket without creating a reusable edge cache. A global S3 access endpoint instead routes requests among several Regional buckets. Multipart upload improves one large transfer's concurrency and recovery. Choose the mechanism that matches the bottleneck.

Byte-range fetching, multipart transfers, batched record layout, multiple prefixes, and edge acceleration can be combined. A global media ingest service might issue multipart uploads through an acceleration endpoint and distribute object keys across prefixes. A data lake scan might keep columnar files at sizes that balance parallelism with request count, then read them concurrently from compute in the same Region. The exam's "batch uploads compared with individual uploads" wording is testing request economics and throughput, but durability and access granularity must still be preserved.

## Versioning, Object Lock, and replication

**S3 Versioning**, the bucket feature that assigns versions to successive object states, protects against accidental overwrite and deletion. A new bucket starts unversioned. After versioning is enabled it can be suspended, not returned to its never-versioned state. An overwrite creates a new current version and leaves the prior full object as a noncurrent version. Each stored version incurs storage charges. A simple delete in a versioning-enabled bucket adds a delete marker as the current version; deleting that marker reveals the prior version. A delete that names a version ID permanently deletes that version if no retention control blocks it.

Versioning is a recovery mechanism, not an automatic retention policy. A busy key can accumulate many complete noncurrent versions, so lifecycle rules should transition or expire them according to the recovery window. MFA delete adds a separate root-user and MFA requirement when permanently deleting versions or changing the bucket's versioning state. It is configured by the root user and is not operated through the console. For most automated protection scenarios, least-privilege policies, Object Lock, replication to a separate account, and lifecycle management are more scalable controls.

**S3 Object Lock**, the write-once-read-many protection for individual object versions, requires versioning and offers retention periods plus legal holds. A legal hold has no expiration date and remains until an authorized principal removes it. A retention period uses governance or compliance mode. Governance mode can be bypassed only by a principal with `s3:BypassGovernanceRetention` that explicitly requests the bypass. Compliance mode cannot be shortened or bypassed by any user, including the account root user, during the retention period. Choose compliance for an immutable regulatory requirement, governance for strong protection with a controlled administrative exception, and a legal hold when the end date is unknown.

Object Lock protects a specified version, not the key forever. A writer can create a new version, and a delete marker can hide a locked version without destroying it. Lifecycle can transition a locked version to a colder storage class, but cannot permanently delete it before retention and legal holds allow deletion. Lock also does not preserve a KMS key. Deleting the encryption key can render an immutable ciphertext unreadable, so key protection, backup, and deletion controls belong in the same compliance design.

**S3 Replication**, the asynchronous copying feature for versioned objects, includes Same-Region Replication (SRR) between buckets in one Region and Cross-Region Replication (CRR) between Regions. Both source and destination buckets must have versioning enabled, and S3 assumes a role from **AWS Identity and Access Management (IAM)**, the service that controls identities and permissions, with permission to read source versions and write replicas. A cross-account destination policy must trust the source role. SRR fits log aggregation, test copies, ownership separation, and compliance within a Region. CRR fits geographic separation, data residency, disaster recovery, and putting copies near remote compute or readers.

Live replication applies to eligible writes made after the rule becomes active. Use S3 Batch Replication for existing objects, previously failed replicas, or objects that became eligible after upload. Replication can change the destination storage class and, with bucket-owner-enforced ownership, make the destination account own replicas. Prefix and tag filters can narrow the rule. For KMS-encrypted objects, opt in to replication and grant decrypt permission on the source key and encrypt permission on the destination key. Contrary to older guidance, eligible SSE-C objects can be replicated automatically when SSE-C is enabled and the replication configuration applies.

Delete behavior is intentionally conservative. Current replication configuration can replicate delete markers when enabled, but permanent deletion of a specific source version is not replicated. That prevents an accidental or malicious hard delete from automatically erasing the replica. Lifecycle actions are not themselves replicated, so configure destination lifecycle rules if replicas should age or expire. Objects already sitting in Glacier Flexible Retrieval, Glacier Deep Archive, or the Intelligent-Tiering archive tiers are not replicated at all until they are restored, which matters when a rule is added to a bucket whose older data has already aged into an archive tier. Replication also does not make a destination a point-in-time transactional copy while asynchronous changes are in flight. Monitor replication status and failed operations rather than assuming that a successful source `PUT` proves the destination copy exists.

S3 Replication Time Control (RTC) adds predictable replication for time-sensitive rules. AWS documents that it replicates most new objects in seconds and 99.9 percent within 15 minutes, with replication metrics and an additional charge. The correct current figure is 99.9 percent, not the older 99.99 percent claim found in some notes. Use RTC when a compliance or recovery point objective requires that service commitment; ordinary CRR remains the lower-cost choice when asynchronous timing is acceptable.

Replication increases durability against account, Region, and administrative failure only when the surrounding controls preserve independence. A destination in a dedicated backup account, with restrictive write and delete permissions, its own KMS key policy, versioning, and perhaps Object Lock, is stronger than another bucket controlled by the same compromised administrator. Replication is not the same as backup because an allowed overwrite, bad data, or optionally replicated delete marker can propagate. Versioning and retention preserve recovery points; replication places them in another failure domain.

## Access control and private network paths

S3 resources are private by default. Access is evaluated from identity-based IAM policies, resource-based bucket or access point policies, applicable VPC endpoint policies, permissions boundaries and session policies, and organization guardrails such as service control policies. An explicit deny wins. For same-account access, an allow in an identity policy or resource policy can be sufficient when no boundary or guardrail limits it. Cross-account access normally needs trust on both sides: the resource owner grants the external principal in a bucket or access point policy, and the principal's account permits the action. Assuming a role in the bucket's account changes the request to that role identity and is often easier to govern.

A bucket policy is a resource policy attached to one bucket. Bucket actions such as `s3:ListBucket` use the bucket ARN, while object actions such as `s3:GetObject` use object ARNs ending in `/*` or a narrower prefix. Conditions make policies useful: `aws:PrincipalOrgID` restricts access to an organization, `aws:SourceVpce` restricts requests to an endpoint, `aws:SecureTransport` denies HTTP, and object-tag condition keys implement attribute-based access. A policy that grants a service access should use source-account or source-ARN conditions when supported to reduce confused-deputy risk.

**S3 Block Public Access**, the preventive control for public policies and access control lists, can apply at organization, account, bucket, and access point levels. S3 enforces the most restrictive applicable combination. Its settings can reject new public ACLs or policies and ignore or restrict access derived from existing ones. The settings do not necessarily erase an old policy or ACL, so removing the block can expose the resource again. Keep all settings enabled unless a reviewed design truly requires anonymous access. A static website endpoint is the common exam exception, although CloudFront with a private S3 origin is the more secure production pattern.

**S3 Object Ownership**, the bucket control for ownership and access control lists (ACLs), defaults to Bucket owner enforced for new buckets. In that mode, ACLs are disabled, the bucket owner owns every object, and policies control access. ACLs are a legacy S3-specific mechanism with coarse grants and no explicit deny or rich conditions. A cross-account uploader no longer needs a `bucket-owner-full-control` ACL when Bucket owner enforced is used. Older questions may propose ACLs for object ownership; prefer Object Ownership and policies unless the scenario explicitly depends on legacy ACL behavior.

**IAM Access Analyzer for S3**, the console view backed by IAM external-access analysis, identifies buckets whose policies or ACLs grant public or cross-account access. It helps find unintended exposure but does not itself grant access or replace Block Public Access. Audit the finding, remove or narrow the policy if unintended, and retain the external grant only when the business relationship requires it.

**S3 presigned URLs**, time-limited signed requests for an object operation, let an application give a client temporary direct upload or download access without distributing AWS credentials or making the bucket public. The URL carries the signer, action, object, and expiration, and it cannot authorize more than the signing principal can do. Treat it as a bearer credential. A CLI or SDK URL can be configured for up to seven days, but one signed with temporary role credentials expires when those credentials expire even if the URL names a later time. Bucket-policy conditions can further restrict signature age, network source, or transport.

```bash
aws s3 presign s3://my-bucket/reports/q3.pdf --expires-in 3600
```

**Amazon Virtual Private Cloud (Amazon VPC)**, the isolated network for AWS resources, can reach S3 privately through gateway or interface endpoints. A gateway endpoint adds S3 routes to selected route tables, has no hourly or data-processing charge, and is normally the most cost-effective path from resources in the same VPC. It supports an endpoint policy that can restrict buckets, actions, and principals, contrary to the old claim that gateway endpoints have no fine-grained permissions. Gateway endpoints do not traverse virtual private network connections, VPC peering, transit gateways, or other Regions.

An interface endpoint uses **AWS PrivateLink**, the feature that exposes supported services through private IP addresses in subnets. It has endpoint-hour and data-processing charges but can be reached through appropriate connected networks and private Domain Name System (DNS), making it useful for on-premises clients or VPCs that cannot use the local gateway endpoint. Neither endpoint removes the need for IAM and bucket authorization. A bucket can explicitly deny requests that do not arrive through the intended endpoint, but such a deny can also lock administrators out of console access, so preserve an authorized recovery path.

**S3 Access Grants**, the scalable data-access feature that maps IAM or **AWS IAM Identity Center**, the workforce access and federation service, identities to bucket, prefix, or object permissions, addresses environments with many datasets and workforce users. It vends scoped temporary credentials after evaluating a grant. Use ordinary identity and bucket policies for a modest set of applications, access points when each application needs its own endpoint policy, and Access Grants when directory identities and a very large grant set would make static policies unwieldy.

Cross-origin resource sharing (CORS) is a browser rule, not an authorization system. A bucket CORS configuration tells browsers which origins, methods, and headers may make cross-origin requests. The request still needs public or signed access to the object. Permissive CORS does not by itself make a private object public, and restrictive CORS does not stop non-browser clients that have valid S3 permissions. Use an exact set of trusted origins and methods for browser applications.

## Encryption and data integrity

All new S3 objects are encrypted at rest by default with server-side encryption using S3-managed keys (SSE-S3), unless the request or bucket configuration selects another supported mode. Default encryption affects new writes; changing it does not re-encrypt existing objects. A Batch Operations copy job can rewrite existing objects under a new encryption mode. Encryption at rest, authorization, immutability, and backup solve different threats and should be designed together.

SSE-S3 manages the data and wrapping keys for the customer and adds no KMS request dependency. Server-side encryption with KMS keys (SSE-KMS) uses KMS for auditable key control. A customer managed KMS key provides a key policy, grants, rotation choices, cross-account use, and the ability to disable or schedule deletion. Uploading needs permission to generate a data key and downloading needs permission to decrypt, in addition to S3 permission. An allow in a bucket policy cannot compensate for a missing KMS key permission. The key must be usable in the bucket's Region, and a cross-account reader needs permission in both the S3 and KMS policy planes.

Dual-layer server-side encryption with KMS keys (DSSE-KMS) applies two independent server-side encryption layers for workloads whose compliance standard requires two layers. It has additional KMS request and cost implications. Do not confuse it with client-side encryption: plaintext still reaches the S3 service over the protected connection. Choose it only when the stated control requires dual-layer encryption, not merely because an object is sensitive.

An **S3 Bucket Key**, the short-lived bucket-level key derived from a KMS key, can reduce KMS request costs by up to 99 percent for SSE-KMS by decreasing calls from S3 to KMS. It is enabled for new objects at bucket or object level and is not supported for DSSE-KMS. Existing objects do not begin using it merely because the bucket setting changes; rewrite them if that benefit is needed. Bucket Keys use the bucket ARN rather than the object ARN as the KMS encryption context and produce fewer KMS events in **AWS CloudTrail**, the API activity audit service, so review policies and audit expectations before enabling them.

Server-side encryption with customer-provided keys (SSE-C) has S3 perform encryption while the client supplies the key on every relevant request. S3 does not retain the key, so losing it makes the object unrecoverable and sharing access with integrated AWS services is difficult. As of April 2026, SSE-C is disabled by default for new general purpose buckets and for existing buckets in accounts that had no SSE-C objects. A workload with a specific requirement can deliberately enable it, then send the required headers. Most new designs should use SSE-KMS for customer-controlled keys or client-side encryption for requirements that S3 must never receive plaintext.

Client-side encryption encrypts before upload and decrypts after download. S3 stores ciphertext and cannot supply plaintext to services that lack the client key and decryption logic. The application owns key availability, rotation, metadata compatibility, and recovery. It is the answer when the requirement explicitly says AWS must not see plaintext or when parts of one object need different cryptographic protection. It is not the lowest-operational-overhead option for ordinary encryption-at-rest compliance.

Transport Layer Security (TLS) protects data in transit to S3 HTTPS endpoints. Current AWS service endpoints require at least TLS 1.2. A bucket policy can explicitly deny any request where `aws:SecureTransport` is false:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Deny",
    "Principal": "*",
    "Action": "s3:*",
    "Resource": ["arn:aws:s3:::example", "arn:aws:s3:::example/*"],
    "Condition": {"Bool": {"aws:SecureTransport": "false"}}
  }]
}
```

Checksums validate accidental corruption in transit or storage; encryption protects confidentiality and integrity against attackers with different assumptions. S3 validates supported upload checksums server-side and stores checksum information with the object. An ETag may help with conditional operations, but it is not a universal checksum. The exam can place all three in one design: TLS for the network, SSE-KMS or client encryption for confidentiality and key control, and a checksum for end-to-end data integrity.

## Access Points, global routing, and response transformation

**S3 Access Points**, named endpoints with their own policies and network controls, simplify shared datasets that serve many applications. Instead of growing one bucket policy to express every consumer, create an access point for each application or team, give it a policy for the necessary prefixes and actions, and delegate access-point authorization from the bucket policy. The access point policy and underlying bucket policy are evaluated together. An access point can be restricted to a VPC, can have its own Block Public Access settings, and supports object operations rather than bucket administration such as creating replication rules.

Access points can be associated with a bucket in the same account or another trusted account, but the bucket owner retains control through the bucket policy. An application addresses an access point ARN or alias instead of the bucket endpoint. This does not copy or partition the objects. Every access point still reaches the same underlying dataset. The default quota is 10,000 access points per Region per account and is adjustable, which gives large organizations much more policy space than one bucket policy.

**S3 Multi-Region Access Points**, global endpoints that route S3 data requests among buckets in several Regions, use the AWS global network to select the closest active Regional bucket. A Multi-Region Access Point changes routing, not storage. It does not inspect whether the selected bucket contains the requested key and does not replicate objects. Configure CRR, often bidirectional replication, so every active bucket can fulfill reads after globally routed writes. Without replication, a correctly routed `GET` can return `404 Not Found` because the closest bucket lacks the object.

The same endpoint can support active-active proximity routing or active-passive recovery. Failover controls change Regional routing status and redirect new data requests away from a disrupted Region within minutes. They do not terminate existing connections or make asynchronous replication synchronous. A global application therefore needs a full recovery design: compatible bucket policies and KMS keys in each Region, replication and replication monitoring, application retry behavior, a chosen conflict model for writes, and tested failover and failback procedures.

Do not confuse the three access features. A regular access point is an application-specific endpoint and policy for a shared dataset, generally with a Regional scope. A Multi-Region Access Point gives one global hostname and proximity or failover routing across Regional buckets. A presigned URL delegates one signed operation for a limited time. None of them by itself makes data public, adds replicas, or converts object storage into a filesystem.

**S3 Object Lambda**, the feature that invokes an AWS Lambda function to modify an S3 `GET`, `HEAD`, or `LIST` response, leaves the source object unchanged. **AWS Lambda**, the serverless function execution service, receives access to the original response through a supporting access point, performs a transformation, and returns a caller-specific result. Existing use cases include masking personally identifiable information, resizing or watermarking images, converting formats, and filtering a listing without storing a transformed copy for each audience.

As of November 7, 2025, Object Lambda is available only to existing customers already using it and select AWS Partner Network partners. Existing customers can continue, but AWS does not plan new capabilities. New designs should transform on ingest, process in the client, or invoke Lambda through a supported application or CloudFront pattern. The exam may still name Object Lambda and expect "transform the response without changing the stored object," but a current architecture recommendation must include its availability status and an alternative for a new customer.

> **Professional depth.** A Multi-Region Access Point is not a magic consistency boundary. Writes route to the closest active bucket, and CRR later propagates them. If two Regions update the same logical key before replication converges, the application needs a conflict strategy. Version IDs are Region-specific, and routing can expose different current versions during the interval. Use immutable keys, a single-writer design, or application metadata that chooses a canonical version when correctness matters more than active-active writes.

## Static websites, event notifications, and application integration

**S3 static website hosting**, the general purpose bucket feature that serves index documents, error documents, and redirects, supports client-side HTML, style sheets, scripts, images, and other static objects. It does not run server code. The direct S3 website endpoint supports HTTP, not HTTPS, and requires public read access. That conflicts with the default Block Public Access posture and does not work for anonymous reads of SSE-KMS objects.

For a secure production static site, keep the bucket private and put CloudFront in front of the S3 REST endpoint with origin access control. CloudFront supplies HTTPS, caching, a custom domain, and viewer-access controls while the bucket policy permits only the distribution. AWS now recommends **AWS Amplify Hosting**, the managed web deployment and hosting service backed by CloudFront, for many static web projects. On an exam, "host a simple static site at the lowest infrastructure cost" can still point to S3 website hosting; "HTTPS, private origin, and global caching" points to CloudFront rather than a public website endpoint.

Cross-origin resource sharing matters when browser code from one origin calls an S3 REST endpoint at another origin. Configure the allowed origin, method, and request headers that the application actually needs. It is not required merely because CloudFront has an S3 origin, and it does not authenticate the browser. Presigned URLs, identity federation, or a public-read policy still supplies authorization.

**S3 Event Notifications**, the event integration for object activity, can react to object creation, removal, restoration, replication, lifecycle, tagging, and other supported event types. Direct destinations include standard **Amazon Simple Notification Service (Amazon SNS)** topics, the managed publish-and-subscribe service; standard **Amazon Simple Queue Service (Amazon SQS)** queues, the managed message queue; Lambda functions; and **Amazon EventBridge**, the managed event bus and routing service. Direct S3 notification destinations do not support SNS FIFO topics or SQS FIFO queues. EventBridge can route matching S3 events to a broader target set and supplies richer filtering.

Notifications are designed for at-least-once delivery and are not guaranteed to arrive in event order. A consumer must be idempotent and tolerate duplicate or delayed messages. Events for the same object include a sequencer value that can help compare ordering for that key. An event is a signal to inspect or process state, not an exactly-once transaction. If one durable consumer must absorb bursts and retry independently, send notifications to SQS. If several subscribers need the same event, publish to SNS or route through EventBridge. Invoke Lambda directly when processing is short, retry behavior is acceptable, and the fewest components matters.

Avoid notification loops. A Lambda function triggered by writes to a bucket should write its result to a different bucket or to a prefix excluded by the notification filter. Prefix and suffix filters can route only source objects such as `incoming/*.jpg`. Destination resource policies must allow S3 to publish or invoke, and source conditions should limit that trust to the intended bucket.

Event notifications and replication serve different needs. Replication copies object bytes and metadata according to a rule. A notification tells another system that an event occurred and may be lost only within the documented delivery model, so the target performs its own business processing. Inventory supplies a scheduled authoritative list for reconciliation. A resilient pipeline often uses an event for low-latency work and a periodic inventory comparison to find and repair drift.

## Inventory, bulk operations, and monitoring

Inventory produces daily or weekly CSV, Apache Optimized Row Columnar (ORC), or Apache Parquet files for a bucket or shared prefix. It can list current versions only or all versions and include selected fields such as size, storage class, encryption, replication status, checksums, Object Lock state, and tags. The destination bucket must be in the source bucket's Region, but it can be owned by another account. Inventory does not call the synchronous `List` API to audit the source and does not consume the bucket's request rate.

Inventory is scheduled, so it is not the source for an immediate answer to "does this key exist now?" Use a strongly consistent `HEAD`, `GET`, or `LIST` for current application state. Use Inventory for compliance evidence, periodic reconciliation, analytics over object populations, and a manifest for bulk jobs. Its output is not guaranteed to be sorted. A cross-account destination policy and, when selected, an appropriate KMS key policy must allow S3 to deliver the report.

Batch Operations reads an S3-generated or user-supplied manifest, assumes a job role, applies one operation to each named object, tracks progress, and can write a detailed completion report. Supported patterns include copy, restore from archive, replace tags or ACLs, apply Object Lock retention or legal holds, invoke Lambda per object, and Batch Replication. Jobs handle billions of objects and exabytes of data; several operation types support manifests of up to 20 billion objects. Use a completion report and sample validation because a completed job can contain failed individual tasks.

Batch Operations is not for low-latency processing of each newly uploaded object. Use an event-driven pipeline for that. It is the answer for "change encryption on billions of existing objects," "restore an archive collection," "add a legal hold to a known population," or "replicate objects that existed before CRR." A manifest defines scope, so review it before approving a destructive or expensive operation. The role needs both Batch Operations permissions and the underlying S3, KMS, Object Lock, or Lambda permissions needed by the selected action.

**Amazon CloudWatch**, the metrics, logs, alarm, and dashboard service, receives S3 daily storage metrics at no additional charge. Optional request metrics operate at one-minute intervals, are billed like custom metrics, and can be filtered by bucket, prefix, tag, or access point. They include requests, bytes, latency, and errors useful for alarms on `4xx`, `5xx`, or performance. Delivery is best effort, so request metrics are operational signals rather than a billing ledger or immutable audit record.

CloudTrail answers who called an API, from which identity and address, and when. Bucket-level management events and object-level data events have different selectors and cost implications, so a trail intended to audit `GetObject` and `PutObject` must include S3 data events for the chosen buckets. S3 server access logging produces detailed access records in a destination bucket and can support traffic analysis. Use CloudTrail for identity-centered API auditing, server access logs for detailed request records, and CloudWatch for metrics and alarms.

**S3 Storage Lens**, the S3 analytics and recommendation dashboard across buckets, accounts, Regions, storage classes, and optionally an AWS organization, supplies daily organization-scale visibility. Free metrics cover storage and management posture. Paid advanced metrics add categories such as activity, status-code, cost optimization, data protection, and performance, plus prefix aggregation, contextual recommendations, longer history, and CloudWatch publishing. Metrics can be exported daily to S3 in CSV or Parquet.

Storage Lens is broader than Storage Class Analysis and different from Inventory. Storage Lens answers "which accounts and buckets are growing, underprotected, or showing inefficient access?" Storage Class Analysis studies whether a filtered Standard population is a candidate for Standard-IA. Inventory lists individual objects and metadata for audit or processing. A mature design uses Storage Lens to find an organization-wide opportunity, Inventory to identify the exact population, Lifecycle or Batch Operations to act, and CloudWatch and completion reports to verify the result.

## Pricing shape and cost decisions

S3 has no charge based merely on creating an ordinary bucket. The bill is shaped by bytes stored per month in each class, API requests by type, retrieval and restore activity for colder classes, data transferred, acceleration, replication, and enabled management or analytics features. The cheapest storage rate is not necessarily the cheapest workload. Model average object size, object count, retention time, transition count, reads, retrieved bytes, and network destination.

Request economics explain why object layout matters. One million small objects require many `PUT`, `GET`, transition, inventory, replication, and possibly KMS operations, while a smaller number of well-sized objects reduces per-request cost. Large objects may transfer unnecessary bytes when consumers need only one record, so columnar formats, indexes, and range reads balance scan efficiency with request count. Delete and cancel requests have no S3 request charge, but deleting before a class's minimum duration can still create an early-deletion storage charge.

Data transfer into S3 from the internet is generally not charged. Transfer between S3 buckets in the same Region and from S3 to AWS services in the same Region is generally not charged for S3 data transfer, even across accounts. Transfer from S3 to CloudFront is not charged by S3, while CloudFront viewer delivery has its own pricing. Cross-Region replication and internet egress have relevant charges. Gateway endpoints avoid NAT processing charges for VPC-to-S3 traffic; interface endpoints add endpoint-hour and data-processing charges. Transfer Acceleration adds its own transfer charge only when used.

**S3 Requester Pays**, the general purpose bucket setting that moves successful request and data-download charges to an authenticated requester, fits shared public-interest or partner datasets whose owner should not fund consumption. The bucket owner still pays storage. Anonymous requests are not allowed. The requester must be authenticated and explicitly acknowledge the charge with `x-amz-request-payer: requester` or the equivalent CLI or SDK parameter. If the requester assumes a role, the account that owns that role is charged.

Requester Pays does not move every possible cost. For example, on an archive restore the requester pays the request while the bucket owner pays the retrieval charge. Some denied requests from within the owner's account or organization can still be charged to the owner. The exam's simple mapping remains: "share a large dataset, requester pays downloads" maps to Requester Pays, not a public bucket, presigned URL, or lifecycle rule.

Use Standard when frequent access and request simplicity outweigh storage savings. Use Standard-IA for long-lived multi-zone data that needs immediate but infrequent reads, and One Zone-IA only when the single-zone risk is acceptable. Use Intelligent-Tiering for meaningful objects with unknown or changing access. Use Glacier Instant Retrieval when rare reads must be immediate, Flexible Retrieval when minutes to hours fit, and Deep Archive for the longest, least frequently retrieved retention. Use Express One Zone when request latency, not lowest storage price or zone resilience, dominates.

Finally, select the storage service before optimizing its tier. S3 is usually more cost-effective than provisioned block or file capacity for durable blobs, backups, archives, data lakes, and static assets because it scales by stored objects and supports cold tiers. EBS is correct when an instance needs a block device; EFS or FSx is correct when applications need shared file protocols, locks, directories, or Windows and specialized filesystem behavior. Trying to save money by forcing a file workload onto S3 can create more application work than the storage savings justify.

## Professional depth

At organization scale, place datasets in accounts according to ownership and blast radius, not merely business prefixes. **AWS Organizations**, the multi-account governance service, can apply an organization-level S3 Block Public Access policy to roots or organizational units, while service control policies restrict who can weaken encryption, logging, or retention controls. A central data or log archive account can own destination buckets, customer managed KMS keys, and Object Lock settings. Bucket policies using `aws:PrincipalOrgID` admit member-account roles without enumerating every account, while explicit exceptions handle approved external partners.

Use Storage Lens with trusted access for organization-wide usage and protection posture, then delegate operational work to the account that owns the data. Access Points separate application policies when a shared data lake serves hundreds of roles. Access Grants scales human and group access through IAM Identity Center. Keep the bucket policy as a guardrail that delegates only intended access points or organization principals. The 20 KB bucket-policy size limit, 10,000 access points per Region per account, and 10,000 general purpose buckets per account affect governance patterns long before storage capacity does.

For hybrid and migration-scale ingest, match the movement mechanism to connectivity and workflow. **AWS DataSync**, the managed online data transfer service, scans, transfers, verifies, and schedules large file or object datasets into S3. **AWS Transfer Family**, the managed file-transfer endpoint service, accepts protocols such as SFTP for partners while storing data in S3. **AWS Storage Gateway**, the hybrid storage appliance service, exposes file, volume, or tape interfaces backed by AWS storage for applications that cannot switch directly to object APIs. **AWS Direct Connect**, dedicated private network connectivity to AWS, provides predictable hybrid capacity, while multipart upload and Transfer Acceleration address internet-based large-object transfers. Seed large migrations, validate checksums and inventory counts, then use incremental synchronization before cutover.

At billions of objects, per-object work dominates. Inventory is safer than repeated recursive listing for scheduled fleet analysis. Batch Operations replaces custom worker fleets for one operation over a manifest. Aggregate tiny archival records where retrieval and compliance permit, because transition requests, 40 KB Glacier metadata overhead, 128 KB minimums, KMS calls, and replication requests can dwarf raw bytes. Precalculate these costs and test a representative prefix before applying an organization-wide lifecycle or Batch Operations job.

Professional failure modes cross policy planes. CRR can show `FAILED` because the replication role lacks source KMS decrypt, destination KMS encrypt, ownership, or destination policy permissions. A Multi-Region Access Point can route correctly and still return a 404 because replication has not produced the key in that bucket. A lifecycle rule can silently destroy recovery depth by expiring noncurrent versions on both sides. A compliance-locked ciphertext can become unusable if its KMS key is deleted. Monitor each dependency and exercise restore, failover, and key-recovery procedures rather than treating configuration as proof.

Quotas and asynchronous behavior shape rollout. Spread a sudden request-rate increase over prefixes and use retry with jitter. Review KMS quotas before migrating a high-volume bucket to SSE-KMS. Treat event consumers as idempotent, reconcile events against Inventory, and verify Batch Operations completion reports rather than only job status. For recovery point commitments, enable RTC and alarm on replication latency. For archive recovery time objectives, initiate sample and mass restores in a game day because the retrieval tier, object count, restore-request rate, and downstream rehydration all contribute to recovery time.

> **Professional depth.** A migration question often offers "copy everything, then enable replication" as a distractor. Live replication covers eligible new writes after configuration, while Batch Replication covers existing objects. Establish the rule, backfill the inventory with Batch Replication, monitor both paths, and compare source and destination inventory before declaring cutover complete.

## Worked scenario

A medical-imaging company has clinics on three continents, analytics compute in two Regions, and a seven-year retention requirement. New studies arrive over variable internet links, radiologists read recent images frequently, old studies are rarely read but must sometimes appear within minutes, and the security team requires customer controlled keys, immutable copies, and account isolation. Researchers outside the company may download an approved public dataset but must pay its access and transfer charges.

Clinics upload through multipart transfer and use Transfer Acceleration only where measurements show an advantage. Current images land in multi-zone S3 Standard under immutable keys and SSE-KMS with a Bucket Key. Lifecycle moves eligible studies to Glacier Flexible Retrieval after the clinical hot period and expires noncurrent operational versions only after the recovery window. A protected copy is replicated with RTC to a dedicated archive account, encrypted under that account's KMS key and placed under Object Lock compliance retention. An Inventory report reconciles the copies, Storage Lens gives central posture and growth trends, CloudWatch alarms on replication failures, and periodic Batch Operations restores prove that the recovery time objective is realistic.

Applications use VPC gateway endpoints and role-based access; separate Access Points scope the clinical and analytics prefixes. A Multi-Region Access Point supplies one global endpoint for the two active Regional copies, with bidirectional replication and a tested write-conflict policy. The approved research bucket enables Requester Pays, so authenticated researchers acknowledge request charges while the company retains storage cost. Event Notifications through SQS start de-identification processing, with idempotent consumers and a separate output prefix. When the exam asks about this scenario, the keyed answer combines S3 object storage, class and lifecycle choices based on retrieval time, versioning and Object Lock for recovery and immutability, cross-account replication for failure-domain isolation, and the correct access or transfer feature for each path.

## Exam lens

- "Object, file, or block storage for a data lake" maps to S3 object storage; EFS and FSx are file distractors, and EBS is the block distractor.
- "Unknown or changing access pattern with millisecond access" maps to S3 Intelligent-Tiering; Standard-IA is the distractor when the read frequency is not predictable.
- "Infrequently accessed, only copy, immediate retrieval, resilient to an Availability Zone loss" maps to Standard-IA; One Zone-IA breaks the resilience requirement.
- "Rarely accessed archive, immediate retrieval" maps to Glacier Instant Retrieval; Flexible Retrieval is the distractor because it needs a restore.
- "Lowest storage cost and retrieval can take 48 hours" maps to Glacier Deep Archive with Bulk retrieval.
- "Delete current objects but keep recoverable history" maps to versioning plus lifecycle for noncurrent versions and delete markers; expiration alone can accumulate old versions.
- "Write once, no administrator including root can delete before the deadline" maps to Object Lock compliance mode; governance mode has a privileged bypass.
- "Replicate existing objects" maps to Batch Replication; ordinary CRR or SRR live rules cover new eligible writes.
- "Predictable cross-Region replication within 15 minutes" maps to S3 RTC and its 99.9 percent commitment; ordinary CRR is the distractor when timing is contractual.
- "One global S3 endpoint with proximity routing and Regional failover" maps to a Multi-Region Access Point plus separately configured replication.
- "Different access policy and VPC restriction for each application sharing one bucket" maps to S3 Access Points, not separate copies of the dataset.
- "Transform a retrieved object without changing the stored object" maps to Object Lambda for an eligible existing customer; a new customer must use a current Lambda or edge transformation pattern.
- "Private S3 access from instances in one VPC at the lowest network cost" maps to a gateway endpoint; an interface endpoint is the distractor unless connected networks need private IP access.
- "Static website with HTTPS and a private S3 origin" maps to CloudFront with origin access control; the S3 website endpoint supports only HTTP and requires public content.
- "Event-driven processing that absorbs bursts and retries" maps to Event Notifications through SQS; direct Lambda invocation is the distractor when durable buffering matters.
- "Apply one operation to billions of existing objects" maps to Batch Operations using an Inventory or CSV manifest, not one Lambda invocation per untracked list result.
- "Organization-wide growth, protection posture, and cost recommendations" maps to Storage Lens; Inventory is the distractor when aggregate trends rather than an object list are required.
- "Shared dataset where consumers pay download request and transfer charges" maps to Requester Pays; the owner still pays storage and anonymous access is not permitted.

### 1. Selecting an object store (Associate)

A media company stores finished video files, thumbnails, and playback manifests. The data volume grows unpredictably, files are replaced as complete units, and applications retrieve them over HTTPS. The company does not need file locking or block-level updates and wants storage that scales without provisioning capacity.

Which solution will meet these requirements with the LEAST operational overhead?

- **A)** Store the files as objects in Amazon S3.
- **B)** Store the files on an Amazon EFS file system mounted by an application fleet.
- **C)** Attach one large Amazon EBS volume to a processing instance.
- **D)** Create an Amazon FSx file system and expose it to the applications.

<details><summary>Answer</summary>

**Answer: A.** S3 matches whole-object HTTPS access and scales without provisioning a filesystem or block volume. B provides shared NFS semantics that the application does not need and adds filesystem-oriented cost. C supplies block storage to an instance, creates an attachment and scaling constraint, and does not directly serve a distributed fleet. D is appropriate when a workload requires a specific managed filesystem protocol or engine, neither of which appears in the requirements.

*Where this is covered: Object storage and the S3 data model.*

### 2. Private and auditable data access (Associate)

An application in private subnets writes regulated objects to S3. The security team requires a customer controlled encryption key with auditable key use, no public access, TLS in transit, and an S3 path that does not require a NAT gateway. Integrated AWS analytics services must be able to read the objects after receiving permission.

Which combination of steps will meet these requirements? (Select TWO.)

- **A)** Disable Block Public Access and restrict the public bucket policy by source IP address.
- **B)** Configure default SSE-KMS with a customer managed KMS key, grant the application and approved services key permissions, and enable an S3 Bucket Key.
- **C)** Require SSE-C for every upload and distribute the raw customer key to each analytics service.
- **D)** Create an S3 gateway VPC endpoint, restrict endpoint and bucket policies, and deny requests when `aws:SecureTransport` is false.
- **E)** Enable a public-read ACL and use CORS to limit which clients can retrieve objects.

<details><summary>Answer</summary>

**Answer: B and D.** B supplies customer controlled, auditable KMS encryption and reduces KMS request traffic with a Bucket Key. D provides the no-NAT private route, policy boundaries, and enforced TLS. A unnecessarily creates a public access path. C is disabled by default for new buckets, is awkward for AWS service integrations, and requires distributing raw key material. E makes the data public, and CORS is only a browser response policy, not an authorization boundary.

*Where this is covered: Encryption and data integrity.*

</details>

### 3. Immutable regulatory records (Associate)

A broker-dealer must retain each trade record for a fixed period. No user, administrator, or root user may shorten the period or delete a protected version before its retention date. New versions may be written under the same key.

Which solution will meet these requirements?

- **A)** Enable S3 Versioning and MFA delete only.
- **B)** Enable S3 Object Lock and apply a retention period in compliance mode to each record version.
- **C)** Apply Object Lock governance mode and grant administrators bypass permission.
- **D)** Replicate records to another bucket and expire the source immediately.

<details><summary>Answer</summary>

**Answer: B.** Object Lock compliance mode prevents a protected version from being overwritten or deleted before its retain-until date, including by the root user. A preserves versions and makes some destructive actions require MFA, but it does not make the protected version nondeletable to every authorized root action. C explicitly retains a privileged bypass, violating the requirement. D adds a copy but supplies no immutability guarantee for either source or destination.

*Where this is covered: Versioning, Object Lock, and replication.*

</details>

### 4. Global writes and controlled failover (Professional)

A company has active application stacks in three Regions and one S3 bucket per Region. Users must use one endpoint that routes uploads to a nearby active Region. During a Regional disruption, operators must redirect new requests without changing application configuration. Every Regional bucket must eventually contain objects uploaded through any other Region.

Which solution will meet these requirements with the LEAST operational overhead?

- **A)** Publish three Regional bucket endpoints in a configuration file and have every client measure latency and implement failover.
- **B)** Enable Transfer Acceleration on one bucket and copy objects to the other Regions with a scheduled script.
- **C)** Create an S3 Multi-Region Access Point, configure bidirectional Cross-Region Replication among its buckets, and use failover controls to change active routing status.
- **D)** Create one S3 Access Point in each Region and use DNS round robin across the access point aliases.

<details><summary>Answer</summary>

**Answer: C.** A Multi-Region Access Point provides the global endpoint and proximity routing, failover controls redirect traffic, and bidirectional CRR separately synchronizes data written to each Regional bucket. A pushes routing, health, and failover logic into every client. B accelerates long-distance transfers to one bucket but does not provide global multi-bucket routing or prompt replication. D uses Regional policy endpoints and unmanaged DNS distribution, not the managed global routing and failover feature.

*Where this is covered: Access Points, global routing, and response transformation.*

</details>

### 5. Re-encrypting billions of existing objects (Professional)

A company acquires a data lake containing billions of existing SSE-S3 objects. Governance now requires SSE-KMS under a customer managed key. The team needs an auditable managed process, an exact object scope, progress tracking, and a per-object result report. New uploads already use the new default encryption.

Which solution will meet these requirements with the LEAST operational overhead?

- **A)** Wait for default bucket encryption to re-encrypt the existing objects automatically.
- **B)** Configure a lifecycle transition from S3 Standard back to S3 Standard with the KMS key.
- **C)** Send one S3 Event Notification for each historical key to a custom fleet of workers.
- **D)** Generate S3 Inventory, use it as an S3 Batch Operations manifest for a copy job with SSE-KMS, and review the completion report.

<details><summary>Answer</summary>

**Answer: D.** Inventory provides the managed object list, and a Batch Operations copy job rewrites each selected object with SSE-KMS while tracking tasks and producing the required report. A is wrong because changing default encryption affects only new writes. B is impossible because lifecycle transitions storage classes and expiration state, not encryption configuration. C requires custom event generation, worker scaling, checkpointing, and audit logic that Batch Operations already manages.

*Where this is covered: Inventory, bulk operations, and monitoring.*

</details>

### 6. Tiny compliance records at scale (Professional)

A payment company produces billions of 20 KB immutable audit records. Records are retrieved by calendar day, are hot for 30 days, and then must remain for seven years with a 24-hour retrieval objective. A cost review shows that per-object requests and archive metadata would dominate raw storage. The company can change the future object layout but cannot weaken retention.

Which combination of steps will meet these requirements MOST cost-effectively? (Select TWO.)

- **A)** Aggregate future records into independently verifiable daily objects before archiving them.
- **B)** Override the lifecycle minimum-size safeguard and transition every 20 KB object individually to S3 Glacier Flexible Retrieval on day 1.
- **C)** Put every record in S3 Intelligent-Tiering and expect the 20 KB objects to move automatically into archive tiers.
- **D)** Keep the only copy in S3 One Zone-IA for seven years.
- **E)** Apply Object Lock retention to the daily objects and use Lifecycle to transition them to S3 Glacier Deep Archive after the hot period.

<details><summary>Answer</summary>

**Answer: A and E.** A preserves the stated day-level retrieval unit while sharply reducing transition requests and per-object archive overhead. E supplies immutable retention and a cold tier whose Standard restore fits 24 hours. B archives during the hot period, overrides a cost safeguard, and pays overhead on every tiny object. C fails because Intelligent-Tiering does not monitor or auto-tier objects smaller than 128 KB. D places the only records in one zone and does not supply regulatory immutability.

*Where this is covered: Pricing shape and cost decisions.*

</details>

### 7. Charging external data consumers (Professional)

A public research organization owns a large curated dataset in S3. Hundreds of partner accounts run unpredictable downloads, and the organization is willing to pay for storage but must not pay successful request and data-download charges for partners. Partners already authenticate with roles in their own accounts, and anonymous access is prohibited.

Which solution will meet these requirements MOST cost-effectively?

- **A)** Keep normal bucket billing and issue each partner a presigned URL.
- **B)** Copy the full dataset into a separate bucket for every partner account.
- **C)** Enable S3 Requester Pays and require partners to acknowledge requester billing in authenticated requests.
- **D)** Make the objects public and use CORS to list the partner domains.

<details><summary>Answer</summary>

**Answer: C.** Requester Pays charges the authenticated requester's account for successful requests and data downloads while the bucket owner continues to pay storage, exactly matching the cost boundary. A still charges the bucket owner because a presigned URL uses the signer's authorization and does not change billing responsibility. B duplicates storage and operational management for every partner. D permits anonymous public access, leaves charges with the owner, and misuses CORS as an access-control mechanism.

*Where this is covered: Pricing shape and cost decisions.*

</details>

### 8. An unpredictable archive (Associate)

A research team stores large experiment outputs for several years. Some projects become active again without warning and then read their objects frequently for a month. Other projects are never opened again. The team needs millisecond access to any nonarchived object and wants storage cost to adapt without maintaining per-project lifecycle schedules.

Which solution will meet these requirements with the LEAST operational overhead?

- **A)** Store every object in S3 Standard-IA and accept retrieval fees.
- **B)** Store the objects in S3 Intelligent-Tiering with the optional archive tiers disabled.
- **C)** Store every object in S3 Glacier Flexible Retrieval.
- **D)** Store the objects in S3 One Zone-IA.

<details><summary>Answer</summary>

**Answer: B.** Intelligent-Tiering observes changing access and moves eligible objects among its millisecond-access tiers without retrieval fees or project-specific schedules. A assumes a stable infrequent pattern and can add retrieval fees during a project's active month. C requires restores and therefore does not provide millisecond access to an archived object. D also assumes infrequent access and introduces a single-zone failure domain that the scenario never accepts.

</details>

### 9. Replicating a complete dataset (Associate)

A company has a versioned S3 bucket containing several years of documents. It must create a copy in another Region. Existing objects must be copied, and at least 99.9 percent of new objects must arrive in the destination within 15 minutes.

Which combination of steps will meet these requirements? (Select TWO.)

- **A)** Configure Cross-Region Replication with S3 Replication Time Control for eligible new writes.
- **B)** Create a Multi-Region Access Point and rely on it to copy every object.
- **C)** Run S3 Batch Replication for the objects that existed before the live rule.
- **D)** Configure S3 Event Notifications to invoke a function that lists and copies the entire bucket after each upload.
- **E)** Move the source objects to S3 One Zone-IA before enabling replication.

<details><summary>Answer</summary>

**Answer: A and C.** A gives eligible new objects the documented RTC timing commitment, while C backfills objects that predate live replication. B routes requests but does not copy data. D builds an expensive, duplicate-prone full-bucket scan and still supplies no replication timing commitment. E changes storage class and resilience but neither copies old objects nor guarantees delivery of new ones. Both buckets also need versioning and the replication role permissions described in the unit.

*Where this is covered: Versioning, Object Lock, and replication.*

</details>

### 10. Lowest-cost long retention (Associate)

An insurer must retain claim evidence for ten years. Auditors retrieve a small selection less than once a year and can wait up to 24 hours before a requested object becomes readable. The insurer wants the lowest storage cost and can accept a restore workflow.

Which solution will meet these requirements MOST cost-effectively?

- **A)** Store the evidence in S3 Standard-IA.
- **B)** Store the evidence in S3 Glacier Instant Retrieval.
- **C)** Store the evidence in S3 Glacier Deep Archive and use Standard retrievals.
- **D)** Store the evidence in S3 Glacier Flexible Retrieval and use Expedited retrievals.

<details><summary>Answer</summary>

**Answer: C.** Deep Archive targets data accessed less than yearly and Standard retrieval normally completes within 12 hours, inside the 24-hour requirement, at the lowest long-term archive storage tier. A pays for immediate access that is not required. B likewise preserves millisecond access and is intended for more frequent archive reads. D restores faster than needed and Expedited retrieval adds premium request and retrieval cost.

*Where this is covered: Storage classes and retrieval behavior.*

### 11. Securing a static website (Associate)

Which solution will meet these requirements?

- **B)** Enable the S3 website endpoint and attach a certificate directly to that endpoint.
- **C)** Give every reader a seven-day S3 presigned URL for the index document.

### 12. Low-latency temporary objects (Associate)

A rendering fleet repeatedly reads and writes reproducible intermediate objects. The fleet runs in one Availability Zone, requires consistent single-digit millisecond object access, and can rebuild the dataset if the entire zone is lost. No versioning or cross-Region replication is required.

Which solution will meet these requirements with the LEAST latency?

- **A)** Use S3 Express One Zone in a directory bucket colocated with the fleet.
- **B)** Use S3 Standard in a general purpose bucket in the same Region.
- **C)** Use S3 One Zone-IA in a general purpose bucket.
- **D)** Use S3 Glacier Instant Retrieval in a general purpose bucket.

<details><summary>Answer</summary>

**Answer: A.** Express One Zone is designed for consistent single-digit millisecond access from compute colocated in one zone, and the reproducible dataset accepts that failure domain. B is durable multi-zone general-purpose storage but does not target the same latency. C is for infrequently accessed data and adds retrieval fees. D is an archive class for rare access, not a high-frequency intermediate-object store, even though its retrieval is measured in milliseconds.

*Where this is covered: Buckets, keys, consistency, and bucket types.*

</details>

## Summary

Choose S3 when a workload can use complete objects rather than block devices or shared-file semantics. Start with the access pattern: Standard for frequent reads, Intelligent-Tiering for changing behavior, Standard-IA for infrequent multi-zone data, One Zone-IA for reproducible data, Glacier Instant Retrieval for immediate archive reads, Flexible Retrieval for minutes to hours, Deep Archive for the coldest retention, and Express One Zone for latency-sensitive single-zone access. Automate known age and retention rules with Lifecycle, and account for object size, requests, retrieval, and minimum-duration charges. Protect data with policies, Block Public Access, private endpoints, TLS, the appropriate encryption mode, versioning, Object Lock, and independently governed replication. Use Access Points for per-application policies, Multi-Region Access Points for global routing, and presigned URLs or Requester Pays for controlled external access. Scale transfers with multipart operations, ranges, prefixes, and measured acceleration. Use Event Notifications for immediate workflows, Inventory for scheduled object catalogs, Batch Operations for fleet changes, CloudWatch and CloudTrail for operations and audit, and Storage Lens for organization-wide optimization.
